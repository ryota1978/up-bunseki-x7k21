# ユナイテッドファーマシー 配布物管理アプリ ／ 開発依頼書（第2版）

このドキュメントをそのまま Claude Code に渡してください。
第1版からの引き継ぎです。プロトタイプ（Claudeのアーティファクト機能上で動くReact単体アプリ）を、
**独立した本物のWebアプリとして作り直すこと**が目的です。

---

## 0. 依頼内容（最初に読んでください）

薬局チェーン「ユナイテッドファーマシー」（6店舗・スタッフ29名）で使う、**店舗配布物の進捗管理アプリ**です。

プロトタイプは Claude 上のアーティファクト機能（簡易的な共有保存の仕組み）で動かしていましたが、
**保存が不安定で、複数端末間のデータ共有が信頼できない状態**になりました。何度再試行しても保存に失敗する、
公開するたびにURLが変わってしまう、内蔵ブラウザで機能が壊れる、といった問題が連続して起き、
実務での常用に耐えないと判断しました。

**今回の開発の目的は、これらの不安定さを構造的に解消し、きちんと動く独立アプリとして作り直すことです。**
機能面はプロトタイプでほぼ固まっているので、大きな仕様変更は不要です。土台を作り直してください。

### 依頼者について

- 依頼者（廣岡）は**プログラミング経験がありません**
- サーバー設定に詳しい人が社内にいません（前回確認済み）
- そのため、以下を必ず守ってください。

1. 専門用語には必ず短い補足をつける
2. 手作業が必要な場面では、**作業を止めて1ステップずつ提示し、完了を確認してから次に進む**
3. 一度に大量の作業を指示しない
4. 選択肢がある場面は「おすすめはこちら、理由は〇〇」と明示する
5. 設定は可能な限りシンプルな構成を選ぶ

## 1. 重要：今回のトラブルから得た教訓（必ず守ること）

**このセクションは、前回の失敗を繰り返さないための最重要事項です。実装前に必ず目を通してください。**

### 1-1. アプリのURLは絶対に変えないこと

前回、機能を直すたびに「公開」をやり直した結果、そのたびに**全く別のURLが発行され**、
過去に送ったリンクと最新のリンクが別物として扱われてしまいました。加藤さん・助田さんが
それぞれ別バージョンを開いていて、「データが共有されない」という混乱が長時間続きました。

今回は、**一度デプロイしたら、その後の更新はすべて同じURL上で反映される**構成にしてください
（Vercelなどの通常のホスティングであれば、これは自然に満たされます）。加藤さん・助田さんに渡すリンクは
**最初から最後まで1つだけ**にしてください。

### 1-2. アプリを何かの中に埋め込まない（独立ページとして動かす）

プロトタイプは Claude のアーティファクト表示（内側の枠＝iframe）の中で動いていたため、以下の不具合が起きました。

- ブラウザ側でマイクを許可していても、埋め込みの枠の中では許可が正しく渡らず、**音声入力が使えなかった**
- 共有ボタンから「ホーム画面に追加」をしても、**アプリのURLではなく親ページ（claude.ai）のURLが登録されてしまい**、
  ホーム画面のアイコンをタップしても目的のアプリが開けなかった

今回作るアプリは、**それ単体で完結した通常のWebページ**にしてください。何かのビューア・別サービスの枠の中に
表示される形は避けてください。これにより、上記2つの問題は構造的に発生しなくなるはずです。

### 1-3. 「ホーム画面に追加」が正しく機能するようにする

上記1-2を満たしたうえで、**PWA（Progressive Web App）としての最低限の設定**（`manifest.json` の設置、
`start_url` に実際のアプリURLを指定、アイコン画像の用意）を行ってください。これにより、
iPhoneのSafariで「共有」→「ホーム画面に追加」をしたときに、正しくアプリのURLがホーム画面のアイコンに
登録されます。前回のように、依頼者側でショートカットアプリを使った回避策を取らずに済むようにしてください。

### 1-4. 「保存できました」と表示された内容は、必ず実際に保存されていること

プロトタイプでは、保存ボタンを押しても失敗することがあり、しかも失敗の原因が分かりにくいものでした。

- 保存処理は必ず**成功／失敗が明確に分かる**ようにしてください（成功時は緑のチェック、失敗時は理由が
  分かるメッセージ、など）
- 失敗した場合は、**自動で複数回リトライ**し、それでも失敗する場合は依頼者が原因を追えるレベルの
  エラーメッセージを出してください（「通信エラー」ではなく「サーバーに接続できませんでした。時間をおいて
  再度お試しください」など、行動につながる表現に）
- 「保存中に見た目だけ成功表示になったが実際は保存されていない」という状態は絶対に作らないでください

### 1-5. LINE WORKSなど社内ツールのアプリ内ブラウザを想定した検証をすること

社内ではLINE WORKSでリンクをやり取りする場面が多く、その内蔵ブラウザ（アプリ内WebView）で開かれると、
Safari本体と挙動が異なり、様々な機能が動かなくなることが分かりました。開発時に、**LINE WORKSやLINEなどの
アプリ内ブラウザで実際に開いて動作確認**をしてください。もし内蔵ブラウザでは動作保証が難しい場合は、
その旨を依頼者にはっきり伝え、「外部のSafari/Chromeで開いてください」という案内文を一緒に用意してください。

## 2. 技術構成の方針

### 推奨構成

| 役割 | 推奨 | 選定理由 |
|---|---|---|
| フレームワーク | Next.js（App Router / TypeScript） | 画面とサーバー処理を1つにまとめられる |
| データベース | Supabase（無料枠） | 画面上の操作でDBが作れる。SQLを直接書かずに済む |
| リアルタイム同期 | Supabase Realtime | 複数端末での即時反映に対応（前回の20秒ポーリングより確実） |
| 公開先 | Vercel（無料枠） | GitHub連携で自動公開。URLが変わらない |
| スタイル | Tailwind CSS | 追加設定が不要 |
| PWA対応 | next-pwa 等 | ホーム画面追加を正しく機能させるため |

別構成を採る場合は、必ず先に依頼者へ理由を説明し、了承を得てから進めてください。

### 環境変数

`.env.local` に必要な値を、**どこからコピーしてくるのか画面の場所まで含めて**案内すること。
`.env.example` を用意し、値は空にしておくこと。

## 3. ログイン・利用範囲の扱い

**利用者は加藤さん（代表）・助田さん（本部）の2名に限定したいという要望が出ています。**
今のプロトタイプはリンクを知っていれば誰でも編集できる状態で、これは意図した設計ではありません。

### 推奨方式

1. アプリを開くと、**合言葉（共通パスワード）1つ**を入力する画面が出る
2. 通過後、**「加藤」「助田」のどちらかを選ぶ**（この2択のみ。他のメンバーは選択肢に出さない）
3. 選んだ名前は端末に記憶し、次回から自動で復帰する
4. 更新履歴に「誰が触ったか」として記録される

店舗スタッフ29名分のデータは、これまで通りメンバー一覧として扱いますが、**アプリにログインして操作するのは
加藤さん・助田さんの2名のみ**という前提で設計してください。他のスタッフは、印刷された一覧や、
2人からの共有によって間接的に情報を受け取る運用を想定しています。

この方式で問題ないか、実装前に依頼者へ必ず確認してください。

## 4. 機能仕様

プロトタイプで実装済みの内容です。**すべて引き継いでください。**

### 4-1. データ構造

#### メンバー（member）

| 項目 | 内容 |
|---|---|
| store | 店舗名（必須） |
| person | 担当者名（**任意・空でも登録可**） |

初期データは第6章に29組すべて記載。「【全店舗】」など店舗ではない通知枠も同じ形で登録されている。

#### 案件（task）

| 項目 | 内容 |
|---|---|
| title | タイトル（必須） |
| member_id | 紐づくメンバー（必須） |
| content | 内容メモ（任意・複数行可） |
| due | 期日（任意。空＝期日なし） |
| meeting | 「会議への転載リスト」フラグ（true/false） |
| jimu | 「医療事務ミーティング」フラグ（true/false）※meetingとは独立、両方trueにできる |
| by_store | 店舗ごとの済チェック方式を使うか（true/false） |
| done | 通常方式のときの完了フラグ |
| stores_done | 店舗別方式のときの、店舗ごとの完了状態（下記4-2参照） |
| created_at / created_by | 作成日時・作成者 |
| updated_at / updated_by | 最終更新日時・更新者 |

### 4-2. 完了（済）の扱い

進捗段階は廃止し、**「済」のみのシンプルな管理**にしています。

- 通常の案件：カードに「済にする」ボタンひとつ。押すと完了リストへ移動
- 店舗全体向けの案件（by_store = true）：**鵜方・射和・神久・岡本の4店舗**それぞれにチェックボタンが並ぶ。
  押した店舗だけ「済」になり、進捗が「2/4」のように表示される。4つ全部そろうとその案件が完了扱いになる。
  「すべて外す」「全店舗 済」の一括操作ボタンも用意する
- 案件追加時、店舗ではなく担当者のいないメンバー（【全店舗】など）を選ぶと、自動で「店舗ごとに済を入れる」
  設定がオンになる（手動でも切り替え可能）

### 4-3. 期日

- 任意入力。カレンダー選択に加え「今日 / 3日後 / 1週間後 / 1ヶ月後 / 期日なし」のクイック指定ボタン
- 残り日数でバッジの色が変わる（4日以上先＝緑、3日以内＝オレンジ、当日・超過＝赤、未設定＝灰の薄字）

### 4-4. 2つの転載先（会議／医療事務ミーティング）

各案件カードに、**「会議へ」「医療事務へ」の2つの独立したチェック**を置く。両方同時にチェック可能。

- トップページに「会議への転載リスト」「医療事務ミーティング」の2つのボタンを常設。それぞれ件数バッジ付き
- どちらのリスト画面も同じ作り：店舗別／人別／期日順で並び替え、見出しでグループ表示
- 「文章でコピー」：現在の並び順のまま、見出し付きテキストとしてクリップボードへコピー
- 「印刷」：専用レイアウトで印刷
- 各行のチェックを個別に解除できる
- 画面下部に「済んだらチェックを一括解除」（確認あり）
- 一方のリストで表示している案件が、もう一方のフラグも立っている場合、「医療事務にも」のような小さなタグを表示

### 4-5. 並び替え・検索

**案件一覧**：期日順（初期値）／店舗別／人別／新しい順
**メンバー一覧**：登録順（初期値）／店舗名順／担当者順／案件の多い順
**検索**：タイトル・店舗名・担当者名・内容メモを対象

### 4-6. 印刷

ブラウザの印刷機能を使用。画面表示とは別に、印刷専用レイアウトを用意すること。
A4縦・余白14mm・見出しや行が途中で改ページされない・上部に日付と件数。

| 画面 | 印刷内容 |
|---|---|
| 案件一覧 | 表形式。手書き用チェック欄と空欄のメモ欄。並び順・検索の絞り込みが反映される |
| 転載リスト（会議／医療事務共通） | 見出しごとに案件を列挙。書き込み用の罫線付き |
| メンバー一覧 | 店舗・担当者・未処理件数・備考欄の一覧表 |

### 4-7. メンバー管理

- 店舗名のみで登録可能（担当者は任意）
- 修正ボタンでその場編集。**修正しても案件との紐付けは維持される**（担当者交代に対応）
- 削除は確認を挟む。未処理案件がある場合は件数を警告し、「修正する」への切り替えを促す
- 各行に未処理案件の件数バッジ
- **名前選択の画面では、「加藤」「助田」を先頭に固定表示**（第3章のログイン方式に対応）

### 4-8. 音声入力

案件追加時に「音声で追加」ボタンを設置。

- マイクボタンを押して話すと、ブラウザの音声認識でテキスト化される（文字起こし内容は手直し可能）
- 文字起こし結果を、AIモデル（Claude API等）に渡し、以下を自動判定させて追加フォームに反映する：
  タイトル／該当メンバー／期日（相対表現から計算）／内容メモ／会議フラグ／医療事務フラグ／店舗ごと済フラグ
- **自動では登録せず、必ず確認画面（追加フォーム）を経由してから登録すること**
- マイク非対応やアクセス不可の環境では、同じ欄に文字を直接入力しても同様に動作するようにする
- 話し方のサンプル文を、マイクボタンの近くに常時表示しておく（例：「全店舗に連絡です。薬剤師の皆さんへ、
  自主勉強会に出席したら申請してください。期日は特にありません。」）

**独立アプリになれば、埋め込みの制限がなくなるため、プロトタイプで発生していた「マイクの許可が反映されない」
問題は解消されるはずです。実装後、実機で必ず確認してください。**

### 4-9. 削除の制限

**未処理の案件には削除ボタンを出さない。** 修正ボタンのみ表示する。削除ボタンは、**完了（済）した案件にのみ**
表示し、押すと確認を挟んでから削除する。これは誤操作防止のための仕様で、そのまま引き継いでください。

### 4-10. データのやり取り（控え）

サーバー保存が実現しても、依頼者の安心のためこの機能は残してください。

- 「控えを取る」：全データをJSONで書き出し。ファイル保存／テキストコピーの2通り
- 「控えから戻す」：貼り付けて復元。件数を表示して確認を挟む

## 7. 進め方（この順番で作ってください）

一度に全部作らず、**下記の順で、段階ごとに動くものを見せてください。各段階の終わりに
「ここまでで動きます。触ってみてください」と伝え、確認を取ってから次へ進んでください。**

| 段階 | 内容 | 依頼者の作業 |
|---|---|---|
| 1 | 構成の説明・方針合意（第1章の教訓を踏まえた設計であることを含めて説明） | 内容を確認して了承 |
| 2 | Supabase / Vercel / GitHub のアカウント作成 | 手順を1つずつ案内すること |
| 3 | DB設計＋29組の初期データ投入 | 動作確認 |
| 4 | 案件の一覧・追加・済（通常＋店舗別） | 実際に触って確認 |
| 5 | 合言葉ログイン＋加藤／助田の選択 | 確認 |
| 6 | 会議・医療事務の2つの転載リスト | 確認 |
| 7 | 並び替え・検索・音声入力 | **実機のスマホで音声入力を確認すること** |
| 8 | 印刷 | 実際に紙に印刷して確認 |
| 9 | メンバー管理・控え | 確認 |
| 10 | PWA設定（ホーム画面追加の確認） | **依頼者のiPhoneで実際にホーム画面に追加できるか確認すること** |
| 11 | LINE WORKS内蔵ブラウザでの動作確認 | 依頼者環境での実機確認 |
| 12 | 公開（デプロイ）・全員へ案内 | 手順を案内すること。**以後URLが変わらないことを明言すること** |

## 8. 最後に

このアプリの目的は、配布物の対応漏れをなくし、店舗を回る人と会議に出る人が同じ情報を見られるようにすることです。

前回はプロトタイプの段階で「共有できない」「開けない」というトラブルが続き、依頼者に大きな負担をかけました。
今回の開発では、**機能を増やすことより、まず「確実に、安定して動くこと」を最優先**にしてください。
派手な機能追加よりも、地味でも壊れない基盤を優先する判断を歓迎します。

判断に迷ったら、実装を進める前に依頼者へ質問してください。
